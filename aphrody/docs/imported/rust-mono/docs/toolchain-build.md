# Toolchain build for the owner's PC (phase 5 design, not implemented)

Goal: a Rust toolchain (rustc, cargo, rustup integration, rust-analyzer, clippy, rustfmt) built from `compiler/rust` and the pinned forks, tuned for the owner's Windows PC, installed with `rustup toolchain link`.

Rule: nothing compiles on the PC. A first attempt froze the machine on 2026-11-17. **Verified** means observed in the session on 2026-11-17; **assumption** means not tested.

## Target

Verified, from `~/.cargo/config.toml`: host `x86_64-pc-windows-msvc`, Intel Core i7-13700F (Raptor Lake), flags already in use for user crates: `-C target-cpu=native -Zthreads=8 -Zshare-generics=y`, `build.jobs = 6`, `rustc-wrapper = "sccache"`. The comment there records the lesson: eight rustc threads times one job per logical core oversubscribes the PC.

Consumers to optimise for (the owner's list): bun (Rust and C++, JavaScriptCore), chromium, linux, zed, LLVM, wasm, huge vendor trees, a whole-OS monorepo. What they ask of the compiler: fast, parallel front end (huge crates), good incremental and shared-generics behaviour, a recent LLVM, `wasm32` and `wasm32-wasip*` targets, and `lld` for link time.

| GitHub-hosted Windows runner for our organization | Only the standard runner. A full upstream-style PGO dist build does not fit in 6 h on 4 vCPU (assumption from the 8-core/32 GB choice upstream made); a non-PGO `x.py dist` with `llvm.download-ci-llvm = true` and sccache in the GitHub cache probably does (assumption, measure) |
| fr1 (Linux, 12 cores, 45 GB RAM, 352 GB free on /srv/xbuild, clang, lld-link, cmake, ninja, sccache installed; rustc nightly 1.100.0-nightly present; target-cpu list includes `raptorlake`) | Cross-build of an msvc host compiler from Linux is not what upstream CI does. The pieces exist (`lld-link`, `clang`), the missing ones are a Windows SDK/CRT sysroot (e.g. `xwin`, not installed on fr1) and an LLVM cross build for the msvc host. Whether bootstrap completes is an assumption | verified: the tools and hardware; assumption: that the cross build works |
| A Windows VM or instance in our cloud | Works the way upstream CI does; costs money and a Windows license (not evaluated; owner budget policy applies) | assumption |

Recommendation, in order of cost and risk:

1. **Prove the pipeline on fr1 with the Linux host first** (`x86_64-unknown-linux-gnu` toolchain from the same pins, same `bootstrap.toml` flags, run in `/srv/xbuild/rust-toolchain`). This validates the monorepo-to-build wiring, the nested-submodule redirection and the flags with a supported configuration, and yields a usable toolchain for fr1's own builds (bun, LLVM, wasm).
2. **Windows host from GitHub's standard runner** with `download-ci-llvm`, no PGO, sccache cache and split jobs (std/rustc/tools), triggered by `workflow_dispatch`, artifacts uploaded; measure wall time. If it fits within the job limit, this is free and never touches the PC.
3. **Cross build on fr1 with xwin** only if (2) does not fit.

The unified decision is made on the measured wall time of (1) and (2), not before.

## bootstrap.toml options

All keys below exist in the current `bootstrap.example.toml` of rust-lang/rust (verified by reading it today). Values are proposals.

```toml
# compiler/rust/bootstrap.toml (generated by the build wrapper, never committed)
[build]
build = "x86_64-pc-windows-msvc"      # or the host of the machine that builds
host = ["x86_64-pc-windows-msvc"]
target = ["x86_64-pc-windows-msvc", "wasm32-unknown-unknown", "wasm32-wasip1"]
extended = true
tools = ["cargo", "clippy", "rustdoc", "rustfmt", "rust-analyzer", "rust-analyzer-proc-macro-srv", "analysis", "rust-src", "wasm-component-ld", "miri", "cargo-miri"]
docs = false                          # books come from books/*, not from this build
jobs = 0                              # the builder's cores; on a workstation this is the freeze

[llvm]
download-ci-llvm = true               # false only for a custom LLVM from compiler/rust-lang-llvm-project
targets = "X86;WebAssembly"           # fewer backends, faster LLVM, smaller toolchain
ninja = true

[rust]
channel = "nightly"
codegen-units = 1                     # upstream dist uses 1 for the shipped compiler
lto = "thin"
lld = true
jemalloc = false                      # not on msvc
llvm-tools = true
rustflags = ["-Ctarget-cpu=raptorlake"]  # explicit name: the build machine is not the PC, so "native" would bake in the wrong CPU

[dist]
compression-formats = ["xz"]
compression-profile = "balanced"
```

Notes:

- `-Ctarget-cpu=raptorlake`: accepted by the nightly on fr1 (`rustc --print target-cpus` lists `raptorlake`, `alderlake`, `x86-64-v3`; verified). Whether a compiler built with it is measurably faster is an assumption; a portable fallback is `x86-64-v3` (AVX2/BMI2, which the 13700F has).
- PGO and BOLT: `pgo.rustc.generate/use` exist in the file (verified); upstream's `opt-dist` automates them and needs the 8-core class of machine. Out of scope until (1) and (2) are measured.
- `-Zthreads=8` and `-Zshare-generics=y` are flags for compiling user crates (in `~/.cargo/config.toml`), not options of the toolchain build. `parallel-frontend-threads` exists under `[rust]` (verified) and is the build-time analogue.
- Nested submodules (cargo, books, rustc-perf, backtrace) must not be cloned a second time: the wrapper maps `compiler/rust/src/tools/cargo` and friends onto the monorepo's checkouts. How (bind mount, symlink or `--reference`) is open; on Windows a junction is the likely answer (assumption).

## Install on the PC

```sh
rustup toolchain link aphrody <unpacked-toolchain-dir>
rustup default aphrody          # or: cargo +aphrody build
```

`rustup toolchain link <name> <path>` registers a directory that has the `rustc`/`cargo` layout as a custom toolchain, and rustup then runs its proxies. Two things to settle by trial on the PC (assumptions, none run): that the extended components (rust-analyzer, clippy, rustfmt) are found next to `bin/` from the linked directory, and that `rust-src` is laid out where rust-analyzer expects it (`lib/rustlib/src/rust/library`). The artifact comes from the build job as a tarball (`dist` output), is unpacked to a local directory, and nothing else is built locally.
