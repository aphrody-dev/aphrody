# Kernel watch plan

Hand-written. Everything `tooling/kernel-watch` generates (pages, data, probe and lane records, boot logs) is written to the git-ignored private store `.private/kernel-watch/` (override with `KERNEL_WATCH_PRIVATE_DIR`) and is never tracked: it describes machines and the state of the work. Paths below such as `versions.md` or `data/lane/` are relative to `<private store>/watch/`.

## What exists

- `tooling/kernel-watch/sources.toml`: one manifest of every source, host, organisation and satellite site (kernels, sources and hosts are counted by `cli.ts validate`).
- `cli.ts poll`: conditional (ETag, If-Modified-Since), per-source minimum interval, exponential backoff and Retry-After or rate-limit-reset on 429 and 5xx, bounded per run (`--max-sources`, `--budget`), resumable because all state is in SQLite. Items land in a store with FTS5.
- `cli.ts build`: deterministic views (`versions.md`, `kernels/<id>.md`, `state-of-kernels.md`, `data/*.json`) from the store.
- GitHub Actions workflow `aphrody-kernel-watch.yml`: polls on a schedule and checks that the views build. It commits nothing; the poll store lives in the Actions cache, never in git.
- Skill `fw: plugins/aphrody/skills/kernel-watch` for agents.

## Latency

"Real time" here means minutes. GitHub schedules cron at best every 5 minutes, runs start late under load, and may skip runs. The workflow polls every 5 minutes; the sources set their own minimum intervals (5 minutes for kernel.org releases and the mainline tree, 10 to 30 minutes for forges, hours for slow-moving lists). Nothing generated is committed.

## Not done on purpose

- Public site pages: the `aphrody.com` and `aphrody.app` DNS and site roles are frozen until the owner decides them. The generated data is what a site could consume; nothing is published, deployed, and no DNS is touched.
- Sub-minute latency: needs webhooks (GitHub and GitLab push events, kernel.org has none) received by a small always-on endpoint that triggers a poll of one source. Design: a Cloudflare Worker validating the signature and calling `workflow_dispatch` with the source id, so the poller stays the single writer.
- Mailing lists: lore.kernel.org is polled through two list feeds only. Full ingestion (public-inbox git clones per list, threading, patch series state) is a separate job for the build host.
- Alpine has no rc kernel (`linux-edge` is absent from aports); Arch's rc is the AUR `linux-mainline`; RHEL is followed through CentOS Stream source-git because RHEL publishes no kernel API.
- Fedora Bodhi is requested with 40 rows; releases older than the newest few can fall outside that page.

## Phase B (build host only)

Done at structure and dependency level. `tooling/kernel-watch/graph.ts` ran on the build host over blob-less shallow clones under `/srv/xbuild/kernel-watch/` (Linux, Asterinas, Redox kernel, drivers and base, LiberNT branch main-nt10) and wrote `graph/<kernel>.md` and `.json`, each section stamped with the commit it was built from:

- Linux: tree and sizes, languages, MAINTAINERS subsystems, `drivers/*` inventory, Kconfig dependency graph (select, imply, depends on) and Makefile composition, checkpatch and clang-format settings.
- Asterinas and Redox: `cargo metadata` workspace graphs (OSTD, kernel components, drivers), rustfmt, clippy, toolchain and workspace lints; Asterinas syscall coverage from the book's SCML files.
- LiberNT: top-level NT components, CMake module types and the most linked modules.

Not done: a symbol-level code graph (call graph, type graph) of these trees. At millions of lines it needs a dedicated indexer and storage and was out of scope for this pass. The reports are regenerated by hand on the build host, not by the scheduled workflow.

## Test lanes (build host and read-only probes)

The watch above only reads sources. Three lanes test what it reports. None of them runs in CI, none of them runs on the PC, and none of them writes to an upstream. Their hosts are ssh aliases and the lane root directory is a command-line argument; nothing in the repository names a machine address, an account or a path of a host (`tooling/kernel-watch/lanes.toml` holds the aliases and the settings).

| Lane | Runs on | Rerun | Output in the repository |
| :-- | :-- | :-- | :-- |
| Host probe | any machine that can ssh to the target; the target is read only | `bun tooling/kernel-watch/cli.ts probe <host id>` | `data/probe/<id>.json`, `probe.md` in the private store |
| rc lane | build host: docker, QEMU with /dev/kvm, a lane root directory | `bun tooling/kernel-watch/lane-host.ts run --root DIR [--ids a,b] [--if-new]`; `bun tooling/kernel-watch/lane-host.ts install-timer --root DIR` adds the user timer; then `bun tooling/kernel-watch/cli.ts lane-sync --root DIR` | `data/lane/<kernel>.json`, `lane.md` in the private store, a Test lane column in `versions.md` |
| WSL2 kernel | build host | `tooling/kernel-watch/wsl/build.sh ROOT REF MARCH`, `tooling/kernel-watch/wsl/merge-test.sh ROOT MSFT_TAG STABLE_TAG UPSTREAM_TAG` | `data/wsl/*.json`, `wsl.md` in the private store, rows in `versions.md` |

`bun cli.ts build` regenerates every page above from the records in the private store; the records themselves come from the build host.

### Host probe

One fixed read-only command list over ssh: `uname`, `/proc/version`, `pacman -Q` and `-Sl` (the host's own synced databases), `pacman-conf`, and the pending updates computed in a `mktemp` directory with its own temporary database (what `checkupdates` does, without `fakeroot`, and without touching the live database). The newest kernels in the Arch repositories including core-testing and extra-testing, the AUR and the CachyOS repositories are read from the public package API, the AUR RPC and the CachyOS repository listings. Everything is ranked by closeness to the mainline rc like `versions.md`. Tests replay recorded host output and repository bodies (`fixtures/probe`); no test touches ssh.

Proven: the production Arch host's running kernel, its lag in cycles against the rc and the stable kernel, the number of pending updates, and the newest candidates elsewhere. Not proven: anything about how the production host would behave on a newer kernel; the probe never installs or boots anything there.

### rc lane

On the build host, per kernel in `lanes.toml`: the Arch baseline (`linux` from core), `linux-mainline` built from the AUR PKGBUILD at the rc tag inside an archlinux container with core-testing and extra-testing enabled (the documentation package and its toolchain are removed from the PKGBUILD, the source is a local shallow mirror of the tag), and the newest `linux-cachyos-rc` package of the CachyOS repositories the build host CPU can run. Each kernel is installed into a copy of an Arch root filesystem (`pacstrap base`, python, mkinitcpio), booted with QEMU/KVM by direct kernel boot, and a systemd service in the guest runs the smoke suite and reports on a second serial port: boot state, serial login getty, dmesg error, warning, critical and BUG counts against the previous run (else the baseline), `systemd-analyze`, DNS through the user-mode network, `pacman -Syu` with the testing repositories enabled (the kernel package under test is held back), `pacman -Qkk` (ownership notes on runtime directories under /var and /run are ignored and counted), and a small kselftest subset built from the rc tag. Kselftest failures fail a kernel only when it has more than the reference kernel, because some tests fail on any kernel in a minimal guest.

Proven: each recorded kernel boots to a serial login in a KVM guest, its uname is the one in the record, and the checks above pass or fail as listed in `lane.md`. Not proven: hardware, graphics, networking beyond the emulated virtio NIC, suspend, anything that needs a real machine; kselftest coverage is deliberately small. The CachyOS package is whatever the CachyOS repositories carry (they lag the PKGBUILD by one or two rc); the lane does not build the CachyOS PKGBUILD.

### WSL2 kernel

`wsl/build.sh` builds the Microsoft tree at a release tag with `Microsoft/config-wsl` following `README-Microsoft.WSL2` (bzImage, modules, UAPI headers, perf, `gen_artifacts_vhdx.sh`), out of tree, with `-march` and `-mtune` for a target CPU passed through `KCFLAGS`. The boot test is a QEMU direct kernel boot with a tiny initramfs; it shows the uname and the absence of a panic but cannot exercise hv_sock, dxgkrnl (`/dev/dxg`, WSLg GPU) or Hyper-V enlightenments, which exist only on a Windows host. `wsl/merge-test.sh` replays Microsoft's own changes (stable tag to Microsoft tag) onto the mainline rc with `git merge-tree` in a throwaway repository and lists the conflicts, with a plain merge for comparison. The artifacts and their sha256 stay on the build host; publishing them (for example to an R2 bucket with a manifest) is an outward-facing step that needs the owner's yes. `wsl/install-wsl-kernel.ts` prints, and only with `--apply` writes, the `.wslconfig` lines (`kernel=`, `kernelModules=`, `kernelCommandLine=`) after verifying the sha256 sums. Nothing in the repository changes a Windows machine by itself.
