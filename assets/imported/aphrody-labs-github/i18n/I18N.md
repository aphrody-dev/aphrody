# Internationalization standard

Applies to every Aphrody Labs repository, to the developer machines and to all code, files and text.
It applies the W3C Internationalization guidance. Machine-readable rules: [`i18n.toml`](i18n.toml). Checker: [`check.ts`](check.ts).

```sh
bun i18n/check.ts [dir...]            # report; exit 1 on any error finding
bun i18n/check.ts <dir> --fix         # apply the mechanical fixes, then report
bun i18n/check.ts rules               # list every rule with its severity
bun test i18n                         # checker tests
```

A repository overrides any `[config]` key with an `i18n.toml` at its root. A line containing `i18n-ignore` is skipped by the line rules.

## 1. Characters and encoding

- UTF-8 only, for every text file, protocol body, database, log, environment value and commit message (Character Model: one encoding per object, UTF-8, no statistical guessing). UTF-16 and legacy code pages are converted at the boundary, never stored.
- No BOM in UTF-8 files (`bom`). Exception: PowerShell scripts, which Windows PowerShell 5.1 reads as the ANSI code page without it (`bom_allowed`).
- Process text as Unicode code points, not bytes or glyphs. Index and truncate on grapheme clusters (`Intl.Segmenter`, ICU `BreakIterator`, Rust `unicode-segmentation`), never on UTF-16 units or bytes. No code points above U+10FFFF or lone surrogates.
- Compare identifiers and syntax case-sensitively without normalization. Where user text must match, normalize to NFC and apply the Unicode canonical case fold (String Matching: not NFKC, not ASCII folding for non-ASCII vocabularies). Store class names, ids and file names in NFC.
- Escapes (`\u`, `&#x;`) only for invisible or ambiguous characters. No bidi controls inside source code (`bidi-control`, Trojan Source).
- HTTP and HTML declare UTF-8: `Content-Type: text/html; charset=utf-8` and `<meta charset="utf-8">` in the first 1024 bytes of `<head>` (`html-charset-missing`, `html-charset`). CSS omits `@charset`; XML declares nothing but `encoding="UTF-8"`.
- Forms and APIs send and accept UTF-8 only; reject other charsets with 415.

## 2. Files and repositories

- `.editorconfig` at the root with `[*]` `charset = utf-8` and `end_of_line = lf` (`editorconfig-charset`, `editorconfig-eol`). Only PowerShell sections may say `utf-8-bom`; `bat`/`cmd` say `end_of_line = crlf`.
- `.gitattributes` begins with `* text=auto eol=lf` (`gitattributes-eol`), followed by `*.bat text eol=crlf` and `*.cmd text eol=crlf`. Binary files are marked `binary`.
- Working trees hold LF (`crlf`). `core.autocrlf=false` everywhere; line endings come from `.gitattributes`, never from a machine setting.
- Git uses `i18n.commitEncoding=utf-8`, `i18n.logOutputEncoding=utf-8`, `core.quotepath=false` (`git-commit-encoding`).
- File names are NFC, free of control characters, and portable (no trailing dot or space, no reserved Windows names).
- Vendored code, build output, fixtures and upstream forks keep their own bytes: `exclude` in `i18n.toml`, never rewritten.

## 3. Language and direction

- Language tags are BCP 47 (RFC 5646): lowercase language, Titlecase script, UPPERCASE region (`zh-Hans`, `es-419`, `pt-BR`), as short as possible, no underscores (`html-lang-malformed`, `wellFormedLang`). Validate well-formedness, not membership; never keep a hand-written list of valid tags or locales; take subtags from the IANA Language Subtag Registry and locale data from CLDR.
- `zxx` marks non-linguistic text, `und` unknown language. No Unicode tag characters (U+E0000-E007F), no flags for languages.
- Every HTML root declares the document language and direction: `<html lang="..." dir="...">` (`html-lang`, `html-dir`). `lang` and `dir` go on `html`, not `body`. The default is the project's `default_lang` and `ltr`; templates set both from the request locale. Direction comes from the script of the locale (`Intl.Locale#maximize`), never from the country or a hard-coded language list. Unknown direction is `auto`.
- Passages in another language carry their own `lang`; opposite-direction phrases are wrapped in an element with `dir`, or `<bdi>`/`dir="auto"` when unknown (user input, `input`, `textarea`, `pre`). `<bdo>` only to force memory order. Isolation controls (U+2066-2069) only where markup is impossible (attributes, titles). No `<meta http-equiv="content-language">` for text language (`html-meta-content-language`).
- Style with logical properties: `margin-inline-start`, `inset-block-end`, `text-align: start`. Mirror layouts by `dir`, never by language checks. Icons with direction (arrows, back) flip in RTL.
- Text expands (30-40 % is typical) and contracts (CJK); no fixed-width boxes for translatable text. `translate="no"` on brand names and code.

## 4. Strings in code, APIs and data

- User-facing text lives in catalogs, not in code (`ui-string-literal`, `no-i18n-catalog`). Source language comes from the project config, default `en`. Use the library the project already has (FormatJS, messageformat/MF2, i18next, Fluent, gettext, ARB, `@angular/localize`, Paraglide, `Microsoft.Extensions.Localization`, `rust-i18n`). Supported locales are the BCP 47 tags of the catalog files present, never a fixed array.
- Messages are whole sentences with named placeholders and ICU MessageFormat plurals and selects. No concatenating fragments, no `n === 1 ? ... : ...`, no English plural suffixes. Give translators context and a description per message.
- Machine-readable syntax (keys, enum values, error codes, identifiers) stays separate from displayable text and carries no language.
- Every natural-language field in an API or data format lets a consumer determine its language and direction (string-meta). The shape is a Localizable object `{ "value": "...", "lang": "<BCP 47>", "dir": "ltr|rtl|auto" }`, a LanguageMap keyed by tag for multilingual values, and resource-level `language` and `direction` defaults that any string may override. Unknown direction is `auto` (first-strong), unknown language `und`; never assume `ltr`. Consumers apply the metadata, isolate inserted strings directionally and never strip bidi controls from content.
- User input captures language and direction when the content is stored for others, and uses `dir="auto"` while typing.
- Names are one or two free-form fields with no assumed order, length or script (given/family splitting is a display concern); addresses are country-driven templates; no required "first name / last name" pair.

## 5. HTTP APIs and OpenAPI

- Language negotiation: requests accept `Accept-Language` (RFC 9110 `q` values, basic filtering of tags); responses send `Content-Language` for the language actually returned and `Vary: Accept-Language` when it affects the body. A `lang` query or an explicit user setting overrides the header. `Content-Language` is audience metadata, not a text-language declaration.
- Every OpenAPI document declares the `Accept-Language` request parameter and the `Content-Language` response header (`openapi-negotiation`, an error). Documents with natural-language fields (`title`, `description`, `name`, `label`, `message`, ...) define a `Localizable` schema (`value`, `lang`, `dir`) and a `LanguageMap`, or carry `lang` and `dir` fields (`openapi-string-meta`).
- Error responses use a stable machine `code` plus a localizable `message` (RFC 9457 problem details: `title`/`detail` localized, `type` stable).
- Text bodies are `application/json; charset=utf-8` (JSON is UTF-8 by RFC 8259); `Content-Type` of text media states `charset=utf-8`.

## 6. Dates, times, numbers, currencies, units

- Exchange locale-neutral standard formats: ISO 8601 / RFC 3339 for date-times, ISO 4217 currency codes with integer minor units or decimal strings, SI/UCUM unit codes, `.` decimal point and no grouping in data, BCP 47 locale ids. Never parse or emit display strings as data.
- Display only through CLDR/ICU: `Intl.DateTimeFormat`, `Intl.NumberFormat` (currency, unit, compact), `Intl.PluralRules`, `Intl.RelativeTimeFormat`, `Intl.ListFormat`, `Intl.Collator`; ICU4X or ICU4C in Rust/C/C++; `java.time.format`, `NodaTime`/`CultureInfo`, `Temporal` where present. The locale is resolved at run time from the request, user setting or document `lang`, never typed as a literal (`locale-hardcode`: literal `toLocale*String("en-US")`, `Intl.*("fr")`, `MM/DD/YYYY`, `%m/%d/%Y`, `setlocale(.., "en_US")`, `Locale.US`, `new CultureInfo("en-US")`, currency symbols concatenated to numbers).
- Time follows Working with Time and Timezones: instants (logs, ordering, certificates) in UTC; wall-clock events store the IANA zone id (`Europe/Paris`, not `Etc/GMT-1`, not `US/Pacific`) next to the local time, and recompute from it because zone rules change; floating values (birthdays, opening hours) are `PlainDate`/`LocalDate`/`PlainTime`; an offset alone is enough only for past events; never add 24 h for "tomorrow". Let users choose their zone and keep it in their profile.
- Week start, calendars, numbering systems, sort order and first-day rules come from CLDR for the locale. Sorting uses the locale collator, never code-point order; searching normalizes as in section 1.

## 7. Text layout and typography

- Do not assume Latin: no per-character width, no letter-spacing on scripts that join (Arabic, Indic), no `text-transform` on non-cased text, no truncation in the middle of a cluster, line breaking and hyphenation by the platform (`overflow-wrap`, `word-break`, `hyphens`, `lang`-aware), `text-wrap: pretty|balance` where wanted.
- Fonts: the font stack covers every supported script with fallback families, variable fonts when available; `font-synthesis` only where the script allows it (no synthetic italics for CJK or Arabic).
- Vertical writing (`writing-mode`), ruby, emphasis marks and inline spacing for CJK are supported by the platform, not re-implemented. Script requirements: https://www.w3.org/TR/typography/ and the per-script gap analyses.
- Underline, bold and italic follow the script (underline skips descenders and CJK ruby; bold and italic are not universal emphasis).
- Review gestures, colors, imagery and names for cultural fit before localizing; do not embed text in images or video without a localized alternative.

## 8. Documentation, MD and MDX, commits

- Docs are UTF-8 with LF. Source language `en` unless the project sets another; a translated page repeats its structure, declares `lang` in front matter (`lang: fr`, `dir` for RTL) and links to its siblings by BCP 47 tag (`README.fr.md`, `docs/<lang>/...`).
- Code blocks and identifiers are never translated; `translate="no"` or a code fence marks them. Headings keep stable ids (explicit anchors) so links survive translation.
- Commit messages, branch names, tags and issue titles are UTF-8; the subject describes the change in the project's source language; no emoji as meaning.
- Generated reports and logs are UTF-8, LF, timestamps in RFC 3339 UTC.

## 9. Developer machine (user level)

- `git config --global core.quotepath false`, `i18n.commitEncoding utf-8`, `i18n.logOutputEncoding utf-8`, `core.autocrlf false`; a user `~/.editorconfig` with the same `[*]` block as section 2.
- Terminals: PowerShell profile sets `[Console]::OutputEncoding`, `[Console]::InputEncoding` and `$OutputEncoding` to `UTF8Encoding($false)`; Git Bash and Niubash run with `LANG`/`LC_ALL` = a UTF-8 locale (`C.UTF-8` or `en_US.UTF-8`, present on the machine).
- System level (not changed by repository tooling): Windows "Use Unicode UTF-8 for worldwide language support", system locale, and legacy console code page 65001 per application.
- Servers set `LANG=C.UTF-8` (or an installed UTF-8 locale), `TZ` unset (UTC) and never a legacy locale.

## 10. Specification and API review checklist

Before shipping a spec, protocol, file format, API, CLI or UI, answer the W3C short checklist:

1. Natural-language text read by humans: language and direction metadata and support (section 4).
2. Typographically appealing text: scripts, line breaking, justification, emphasis (section 7).
3. Pointing into, fragmenting, concatenating or stepping through text: grapheme units, no concatenated messages.
4. Searching or matching text, syntax and identifiers: normalization and case folding stated (section 1).
5. Sorting: locale collation.
6. Capturing user input: language and direction, locale-specific input methods.
7. Time read by humans or crossing time zones: UTC instants, IANA zone ids, floating types (section 6).
8. Encodings other than UTF-8: none, or a written justification.
9. Markup: i18n features supported; no human-readable text in attribute values or plain-text elements.
10. Names, addresses, dates: flexible models (sections 4 and 6).
11. Data likely to need localization: stored, labelled and retrievable per language.
12. Cultural norms: imagery, gestures, roles adaptable.

Run the W3C Internationalization Checker (https://validator.w3.org/i18n-checker/) against every public page and request an i18n review for new formats (https://www.w3.org/Guide/documentreview/).
